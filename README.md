# Tenders Tracking Service

Сервис отслеживания тендеров: создание, смена статуса с аудитом изменений,
просмотр списка и истории. Backend на FastAPI + PostgreSQL.

## Логика решения

### Слои

```
app/api/            — роуты (FastAPI) + Pydantic DTO для запросов/ответов
app/services/        — бизнес-логика (сервисы) + интерфейсы (abstractions/)
app/dal/              — доступ к данным: Unit of Work, репозитории, ORM-модели
app/dependencies/    — сборка зависимостей FastAPI (DI-провайдеры)
app/bootstrap/        — построение ресурсов приложения (БД, auth) и lifespan
app/exceptions/       — доменные исключения + единый обработчик ошибок
app/cofigurations/   — конфигурация (env), настройка логирования
```

Слои разделены интерфейсами (`AbstractTenderService`, `AbstractUnitOfWork`,
`AbstractTenderRepo`, `AbstractAuthService` и т.д.) — конкретные реализации
подставляются через DI. Это же даёт возможность тестировать сервисный слой
без реальной БД, если понадобится (сейчас тесты используют реальный Postgres,
см. раздел «Тестирование»).

### Паттерны

- **Unit of Work** (`SqlAlchemyUnitOfWork`) — границы транзакции вокруг
  репозиториев. `async with uow:` — commit при успехе, rollback при
  исключении. Для чистых чтений вызывается `uow.mark_read_only()`, чтобы
  не коммитить транзакцию, которая ничего не писала.
- **Repository** (`TenderRepo`, `TenderChangeLogRepo`) — вся работа с БД
  спрятана за интерфейсом, сервис не знает про SQLAlchemy.
- **Пессимистичная блокировка** — смена статуса читает тендер через
  `SELECT ... FOR UPDATE`: два параллельных запроса на один тендер не
  гонятся за данными, второй дожидается первого и видит уже актуальный
  статус (проверено интеграционным тестом с двумя реальными соединениями).
- **Cache-aside (Redis)** — `get_tender_by_id` сначала читает из Redis
  (`AbstractTenderCache`), при промахе идёт в БД и кладёт результат в кэш
  с TTL. `update_tender_status` инвалидирует ключ после успешного коммита
  транзакции — не раньше, иначе откат транзакции мог бы оставить в кэше
  данные, которых в БД никогда не было. Блокирующее чтение перед сменой
  статуса (`get_by_id_for_update`) кэш никогда не использует — ему нужна
  гарантированно свежая строка. Кэш — best-effort: любая ошибка похода в
  Redis гасится внутри `RedisTenderCache` и трактуется как промах, сервис
  остаётся рабочим и без Redis, просто без ускорения.

### Бизнес-правила

- Статусы тендера: `draft → active → {won | lost}`. `won`/`lost` —
  терминальные, обратных переходов нет. Любая другая попытка смены статуса
  отклоняется с `409 Conflict`.
- Каждая смена статуса обязана сопровождаться причиной (`update_reason`) и
  фиксируется в `tender_status_change_log` — полный аудит, кто, когда и
  почему поменял статус.
- `created_by`/`updated_by`/`changed_by` берутся из JWT (claim `sub`), не из
  тела запроса — клиент не может представиться чужим пользователем.

### Аутентификация

JWT в заголовке `Authorization: Bearer <token>`. Сервис — resource server,
токены не выпускает, только проверяет (подпись, `exp`, наличие и формат
claim'а с id пользователя). Валидная подпись означает, что токен выпущен
доверенным источником, использующим тот же секрет (`JWT_SECRET`).

## Технологии

- **FastAPI** + **Uvicorn** — HTTP-слой
- **SQLAlchemy 2.0 (async)** + **asyncpg** — ORM и доступ к PostgreSQL
- **Alembic** — миграции
- **Pydantic v2** — валидация запросов/ответов
- **PyJWT** — проверка JWT
- **Redis** — кэш чтения тендера по id
- **pytest** + **pytest-asyncio** — тесты

## API

Префикс всех эндпоинтов — `/api/v1/tenders`. Везде, кроме отмеченных, нужен
`Authorization: Bearer <jwt>`.

| Метод | Путь | Описание |
|---|---|---|
| POST | `/` | Создать тендер |
| GET | `/` | Список тендеров (фильтр по статусу, пагинация) |
| GET | `/{tender_id}` | Тендер по id |
| PATCH | `/{tender_id}/status` | Сменить статус (с обязательной причиной) |
| GET | `/{tender_id}/changelog` | История изменений статуса |

Полная схема — `/docs` (Swagger UI) после запуска.

## Запуск

### Переменные окружения (`.env`)

```
DB_CONNECTION_STRING=postgresql+asyncpg://user:password@localhost:5432/tenders
DB_ECHO=false
MAX_POOL_SIZE=10
MAX_OVERFLOW=20
POOL_TIMEOUT=30

JWT_SECRET=<секрет, которым подписаны входящие токены>
JWT_ALGORITHM=HS256
JWT_USER_ID_CLAIM=sub

REQUEST_BODY_MAX_SIZE=32768

REDIS_URL=redis://localhost:6379/0
CACHE_TTL_SECONDS=60

LOG_LEVEL=INFO
```

### Установка и миграции

```bash
pip install -r requirements.txt
alembic upgrade head
```

### Запуск сервера

```bash
python run.py
```

## Тестирование

```bash
pytest                    # всё
pytest tests/unit         # без БД, быстро
pytest tests/integration  # нужен доступный Postgres (из DB_CONNECTION_STRING)
```

- `tests/unit/` — изолированная логика (валидация JWT, конфигурация,
  маппинг исключений), без БД.
- `tests/integration/` — сервисный слой, HTTP-слой и гонка за блокировкой
  против реального Postgres. Изоляция — через `SAVEPOINT`: тест видит свои
  же записи, но после теста в БД ничего не остаётся, независимо от того,
  сколько раз код внутри теста вызвал `commit()`.

## TODO — что можно улучшить, но не вошло в текущую сборку

1. **CI-проверка безопасности миграций.** Ничего не мешает смержить
   миграцию, которая упадёт при накатывании на непустую таблицу (например,
   `NOT NULL`-колонка без backfill). Нужна CI-джоба, которая накатывает
   миграции на БД с заранее засеянными данными и ловит такие случаи до
   деплоя, а не во время него.
2. **RBAC / права на свои тендеры.** Сейчас любой аутентифицированный
   пользователь может читать и менять статус любого тендера, не только
   своего. `created_by`/`updated_by` в модели есть, но не используются как
   право доступа — это сознательно отложенное решение, нужно подтверждение
   от заказчика, требуется ли владение вообще.
3. **Отдельная тестовая база данных.** Сейчас интеграционные тесты
   подключаются к той же БД, что указана в `.env` для разработки — если
   `.env` случайно укажет на shared/staging окружение, тесты откроют
   транзакции против него. Нужна явно отдельная тестовая БД (или
   guard-проверка на имя базы). То же самое применимо и к Redis — тесты
   кэша сейчас идут в тот же инстанс, что указан в `REDIS_URL`.
4. **CI в целом.** Кроме проверки миграций (п. 1) — нет автоматического
   прогона тестов и линтеров на каждый push/PR. Пока весь контроль
   качества — ручной.
5. **`WWW-Authenticate` заголовок на 401-ответах.** Небольшое отступление от
   стандарта bearer-авторизации — заголовок не выставляется, что не мешает
   ручным/самописным клиентам, но может мешать generic HTTP-auth тулингу.
6. **Кэш списков и инвалидация по паттерну.** Сейчас кэшируется только
   чтение одного тендера по id; список (`get_tenders`) всегда идёт в БД —
   вариантов фильтра/пагинации много, а точечная инвалидация всех
   затронутых ключей при записи существенно сложнее, чем один ключ на
   тендер. Отдельное решение, если нагрузка на список станет узким местом.
